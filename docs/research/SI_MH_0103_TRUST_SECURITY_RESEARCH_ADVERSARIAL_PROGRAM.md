## Static findings / hypotheses, NOT demonstrated exploit
SR-F01 P0: signed_reader uses bound_identity only in its query; payload RLS permitted() joins login_binding/principal but not external_identity. If a database login credential is separately compromised, deletion of external_identity alone may not revoke direct database reads. Different boundary from the signed gateway. Reproduce strictly in existing synthetic disposable DB using independent sessions; require no continued access after revocation under defined threat model. Compare removing role binding, credential termination, persistent generation/revocation checks and restricting direct network reachability.
SR-F02 P0: read() performs two queries, then returns after transaction closes; credential/scope changes or revocation after final query can race delivery. No defined linearization point or SLA. PostgreSQL documented race caveats. Define separate semantics for future reads, already authorized in-flight reads, writes at commit, and cancellation; orchestrate deterministic barrier tests, separate connections/processes. Do not assert information already delivered can be recalled.
SR-F03 P0: trusted bootstrap/connection factory and per-principal passwords are lab assumptions. All identities' credentials in one compromised process create blast radius. Compare per-tenant or per-service isolated credentials, constrained broker, sender-constrained tokens, separate control/data planes, runtime sandbox. No credential store or direct-login design production decision.
SR-F04 P0: existing threat model TB-04 notes shared Mem0 service key and scope boundary. Need validate source ACL before retrieval and after ranking, revoked candidate denial, tenant separation in vector store/index/cache, prompt and logs. A2 read is synthetic payload, NOT proof of Mem0 integration. LEARN receives only authorized synthetic evaluation contract, no cross-track edits.
SR-F05 P0: MCP/auth bridge not implemented with signed identity; malicious model/tool output is untrusted data, not permission. Test forged tool arguments, confused deputy, token passthrough, session/client mix-up, prompt and memory poisoning, schema/version integrity, egress policy and consent. No public hosts/real credentials. No autonomous writes/approval/DONE.
SR-F06 P1: develop protected=false observed; branch rulesets not fully inspected. CI green does not guarantee independent review or tamper-proof supply chain. Propose explicit governance decision reconciling current direct-publish convention with required PR/status checks, pinned dependencies, SBOM and provenance. Do not change branch settings.
SR-F07 P1: global lock in reader serializes requests; resource exhaustion, DB availability, timeout and side-channel behavior not load-tested. Budget, backpressure, outage, generic deny and timing studies, bounded synthetic load only.
SR-F08 P1: policy metadata and direct boolean helper can be an existence oracle within allowed context; DB FK/error timing can disclose metadata. Test output equivalence, minimize metadata and error differences; no full constant-time claim. Further full code review required; list not exhaustive.

## Candidate architecture comparison (hypotheses)
B0 current SQL exact grant + forced RLS: low service count, local transactional consistency, good baseline; complex policy evolution, privileged role and cross-store boundaries. B1 SQL/RLS + explicit policy engine Cedar (ABAC, schema validation): decoupled semantics and useful independent checks; authoritative attributes and synchronization required. B2 Zanzibar-inspired ReBAC with OpenFGA/SpiceDB plus RLS: graph delegation and project inheritance, consistency mechanisms; separate datastore, stale permission and distributed failure complexity. B3 isolated DB/index/service per tenant or sensitivity tier: blast radius containment; cost, pooling, migration/operations overhead. B4 hybrid RLS and policy service with isolated high-sensitivity data planes; candidate not winner. Compare identical synthetic corpus and authorization matrix, no provider procurement or framework adoption. Authentication separate: OIDC + PKCE for humans, workload mTLS/SPIFFE or appropriately audience-bound credentials for services, delegated task scopes for agents; DPoP/mTLS client support and trust boundaries tested. Do not use a proprietary cipher or home-grown identity provider as novelty. Proprietary differentiation: cross-agent task authorization, provenance, revocation orchestration, evidence and trust policy, independently verified.
