## 2. Research verification and alternatives
Primary documentation verified 2026-11-24:
- RFC 7009 https://www.rfc-editor.org/rfc/rfc7009.html and RFC 7662 https://www.rfc-editor.org/rfc/rfc7662.html : revocation propagation and introspection-cache tradeoff. Signed token expiration alone is not an immediate principal revocation mechanism. Sender constraint is complementary, not a cure for a compromised authorized runtime.
- PostgreSQL 16 RLS https://www.postgresql.org/docs/16/ddl-rowsecurity.html , transaction isolation https://www.postgresql.org/docs/16/transaction-iso.html , explicit locking https://www.postgresql.org/docs/16/explicit-locking.html and application consistency https://www.postgresql.org/docs/16/applevel-consistency.html : statement snapshots, concurrent policy lookup risks, lock/serialization tradeoffs. REPEATABLE READ can retain old authorization state; SERIALIZABLE supplies a serial ordering, not a wall-clock delivery cutoff or external side-effect atomicity. Locking requires consistent enforcement by all mutation paths and bounded contention.
- PostgreSQL 16 role attributes https://www.postgresql.org/docs/16/role-attributes.html and administration functions https://www.postgresql.org/docs/16/functions-admin.html : login authority and backend termination are separate controls; neither recalls released data. Avoid granting session-management or role-management rights to agent-facing service.
- Zanzibar original research https://research.google/pubs/zanzibar-googles-consistent-global-authorization-system/ : external consistency across ACL/content changes. SpiceDB https://authzed.com/docs/spicedb/concepts/consistency and https://authzed.com/docs/spicedb/concepts/read-after-write : freshness revisions and datastore-dependent semantics. OpenFGA https://openfga.dev/blog/query-consistency-options-announcement : stronger consistency mode trades caching for freshness; not equivalent to cross-system commit or delivery fence. Neither external policy engine eliminates need for a trusted PEP and effect enforcement.

Candidate comparison (qualitative, NOT BENCHMARKED):
C0 existing repeated signed verification + RLS: reference only, F01 and late F02 reproduced.
C1 authoritative persistent principal lifecycle/generation + RLS + coordinated login/session invalidation: low dependency count, useful F01 mitigation candidate; existing snapshot/transaction and control-plane compromise limits; generation alone is not a fence.
C2 transactional local authorization/fencing + bounded admission/release registry: align permission checks and protected effects within one authoritative DB, independent gateway output boundary; lock ordering, crashes, cancellation, deadlocks, contention and incomplete distributed atomicity must be tested. Cannot lock until an external recipient actually receives bytes.
C3 Zanzibar-style revision-aware external policy service + RLS: delegation graph and multi-service freshness, extra datastore/availability/revision binding complexity; no demonstrated need at current scale. Cedar and other policy logic may be complementary, not selected.
C4 isolated credential broker and data-plane compartments: reduces compromise blast radius; infrastructure and credential lifecycle costs; does not itself guarantee revocation consistency.
Recommendation: compare C1 and C1+C2 in disposable lab first, then C3/C4 according to risk/measurements. Keep C0 executable baseline. Do not choose product vendors or permanent role-per-agent model. No raw DB credential to models or connector clients; existing direct logins are laboratory test subjects. Broker itself is privileged and must be separately confined/audited.

## 3. Proposed security semantics (operator decision needed)
Distinguish token-specific invalidation, whole principal suspension, membership/grant revocation, workload/DB credential invalidation. An individual revoked token need not disable all credentials of a principal; a whole-principal emergency revoke must remove all associated authority, including independently issued DB sessions within the defined lab scope. Regrant must use fresh explicit approval/new generation, not resurrect stale credentials. A principal and permission generations are authoritative persisted facts, not client claims. Resource-level revocation must not disable unrelated identities/permissions.
- R0 = durable committed admission fence for affected scope: deny new operation admission and reject stale authority; fail closed if authoritative state cannot be verified.
- R1 = completion acknowledgement after demonstrable containment of all affected controlled active sessions/operations, no outstanding release permits; never report REVOKED if uncertain. State ACTIVE -> REVOKING -> REVOKED. Pending/failure remains non-admitting, retry/reconcile idempotently. Measure R1-R0, not arbitrary network receipt times. Acknowledgement means controlled-boundary completion only, not destruction of copies or remote SaaS sessions.
- Read authorization: separate admission, last authorization, protected gateway release point (first irreversible handoff to transport/caller) and client receipt. Proposed conservative policy: no new admission after R0; reads not yet admitted to release at R0 cancel/deny; an already admitted bounded release can finish only while REVOKING, before R1, with explicit tracked limits. For sensitive data prefer buffer and cancel before release where possible. No new protected release after R1. Already emitted bytes cannot be recalled, transport buffers can arrive later. This is not a claim of zero post-R0 bytes under all races. Stronger no-release-after-R0 policy needs atomic coordination at the release boundary, not another check. No streaming in first lab.
- Future writes: mutually ordered authorization/effect commit and revocation in one authoritative transaction where feasible; reject effect commits ordered after revocation, require idempotency and fencing, distinguish external irreversible effects and compensations. No write implementation authorized for X02; write race remains NOT_RUN.
- Availability: bounded lock/transaction/lease budgets, no indefinite wait, no positive completion acknowledgement on timeout, process death or unknown outstanding effects. Stronger consistency may sacrifice availability. Distinguish durable revoke acknowledgement from delivery/containment acknowledgement. All requirements below proposed, no numeric production SLA chosen.
